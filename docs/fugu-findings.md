# Fugu 実測メモ & ベンチ設問集

Phase 0 の実接続で得た Fugu の挙動と、契約判断に効く「実力 vs 裏コスト vs レイテンシ」を
測るための設問集。**サンプルは少数**なので断定ではなく傾向として読むこと。

## 1. モデルの棲み分け(実測)

| モデル | fan-out(裏) | レイテンシ | 位置づけ |
|---|---|---|---|
| `fugu` | **観測範囲で常に 裏=0** | 数秒〜30秒 | 単一モデル的にふるまう。速い |
| `fugu-ultra` | **裏が大量**(例 78%・98%) | 数分(287s / 427s) | マルチエージェントで fan-out。重い |
| `fugu-cyber` | 未確認(要調査) | — | — |

→ **裏（orchestration）が出るのは実質 ultra だけ。** モデル選択がそのまま裏コストの有無に直結。

## 2. 無裏(fugu)時の実力(答え合わせ可能な設問で検証)

| 設問 | 正解 | 結果 |
|---|---|---|
| 平均速度トラップ(60km@30 + 60km@60) | 40 km/h | ✅ 40（45の罠を回避） |
| 偽前提「キュリーの文学賞」 | 受賞していない | ✅ 訂正し実際の2賞を提示 |
| 100日後の日付(2026-07-24起点) | 2026-11-01(日) | ✅ 完全一致 |
| コード生成 `is_balanced` | — | ✅ 実行して **9/9 テスト通過** |
| 存在しない論文の要約 | 「無い」と言うべき | ✅ 「主要DB・既知文献に存在しない」 |
| 存在しない関数 `itertools.superflatten` | 「無い」と言うべき | ✅ 正しく否定 |

**正確性・ハルシネーション耐性ともに良好**（6/6 実質正解、捏造なし、偽前提を訂正）。

## 3. 重要な注意点(2つ)

### (a) 「裏0」でも reasoning_tokens を大量消費
単純なコード生成でも `completion_tokens` の大半が `reasoning_tokens`（例: 744 中 650）。
表示される回答は約94トークン分。**orchestration=0 でも「見えない思考コスト」は別枠で存在**する。
→ 「fugu は安い」と即断できない。ダッシュボードは `reasoning_tokens` も追うべき
（`raw_usage` に入っている。schema 昇格の是非は要ユーザー判断）。

### (b) 思考過程が最終回答に漏れることがある
存在しない論文への回答に、英語の内部メモ
`Then explain... Let's refine the response to` が混入した例あり。
**常用の実用性を測るなら「出力フォーマットの安定性」も評価軸に入れる。**

## 4. 「裏(orchestration)」とは何か(現時点の理解)

Sakana の公開説明では Fugu は「委任・エージェント間通信・成果統合に特化した LM で、
1 リクエストを複数 LLM に振り分け、結果を 1 つの答えに統合する」。

したがって orchestration トークンは、**裏で走る一連の処理の総量**と解釈できる:
タスク分解・どのサブ LLM に何を投げるかの計画・サブ LLM への指示(input)と
その生成(output)・最終統合。

ただし実測の規模（ultra で裏 input 16,328 / output 25,988）から見て、
**「どの LLM に振るかを決める部分」だけではなく、裏で動くサブエージェント群の
やり取り本体（見えない入出力）まで含む**と考えるのが自然。
※ これは公開説明＋トークン規模からの**推測**。内部の実処理は API からは見えない
（だからこそ `raw_usage` を無加工保存して事後に追える設計にしている）。

## 5. ベンチにできる設問カテゴリ(採点自動化できるものを選ぶ)

「正解が機械判定できる」ことが肝（Fugu と将来のローカル LLM を同一問題で比較するため）。

- **自動採点コード生成**: 関数仕様 → 生成コードを**実行してテスト通過数**で採点。
  正規表現/SQL 生成も、サンプルデータに当てて検証。
- **忠実性(要約)**: 与えた原文を要約 → **原文に無い事実を足していないか**を突合（実務版ハルシネーション検査）。
- **偽前提の訂正**: 「なぜ X は(実際はしていない)Y をした?」→ 訂正できるか。
- **存在しない実体**: 偽の論文/API/関数 → 「無い」と言えるか(捏造率)。
- **決定的計算**: 日付/単位/為替換算 → 厳密一致。
- **構造化抽出**: 自由文 → 指定 JSON スキーマ → バリデーションで採点。
- **オーケストレーション誘発**: 多専門家統合タスク → 裏が出るモデル/条件の切り分け。

各設問を「自動グレーダ(実行・完全一致・スキーマ検証)」とペアにするのが
`reasoning-math-benchmark` の grading.py 思想と同じ。Phase 2 でここに合流できる。

## 6. 総括(小サンプルの暫定所感)

- **base `fugu`**: 素直で正確、捏造しにくい、速い。普段使いのモデルとして印象は良い。
- **`fugu-ultra`**: 出力の質は高い(移行計画の例は妥当)が、**裏 78〜98% + 初動数分無音**の
  コスト/レイテンシが重い。「専門家チームを組む代わり」に払う価値がある高価値タスク限定か。
- Fugu の美点として、**裏トークンや reasoning を usage で開示している**点は珍しく、
  事後計測(このプロジェクト)と相性が良い。多くのプロバイダはここを隠す。

> 注意: 本メモは十数プロンプト規模の観測。契約判断は日曜までに溜めた実使用データで
> ダッシュボードが幅つきで示すこと（点推定を信用しない）。
