# Fugu 実測メモ & ベンチ設問集

Phase 0 の実接続で得た Fugu の挙動と、契約判断に効く「実力 vs 裏コスト vs レイテンシ」を
測るための設問集。**サンプルは少数**なので断定ではなく傾向として読むこと。

## 1. モデルの棲み分け(実測)

| モデル | fan-out(裏) | レイテンシ | 位置づけ |
|---|---|---|---|
| `fugu` | **観測範囲で常に 裏=0** | 数秒〜30秒 | 単一モデル的にふるまう。速い |
| `fugu-ultra` | **裏が大量**(例 78%・98%) | 数分(287s / 427s) | マルチエージェントで fan-out。重い |
| `fugu-cyber` | 未確認(要調査) | — | — |

→ **裏（orchestration）が出るのは実質 ultra だけ。** モデル選択がそのまま裏コストの有無に直結。

## 2. 無裏(fugu)時の実力(答え合わせ可能な設問で検証)

| 設問 | 正解 | 結果 |
|---|---|---|
| 平均速度トラップ(60km@30 + 60km@60) | 40 km/h | ✅ 40（45の罠を回避） |
| 偽前提「キュリーの文学賞」 | 受賞していない | ✅ 訂正し実際の2賞を提示 |
| 100日後の日付(2026-07-24起点) | 2026-11-01(日) | ✅ 完全一致 |
| コード生成 `is_balanced` | — | ✅ 実行して **9/9 テスト通過** |
| 存在しない論文の要約 | 「無い」と言うべき | ✅ 「主要DB・既知文献に存在しない」 |
| 存在しない関数 `itertools.superflatten` | 「無い」と言うべき | ✅ 正しく否定 |

**正確性・ハルシネーション耐性ともに良好**（6/6 実質正解、捏造なし、偽前提を訂正）。

## 3. 重要な注意点(2つ)

### (a) 「裏0」でも reasoning_tokens を大量消費
単純なコード生成でも `completion_tokens` の大半が `reasoning_tokens`（例: 744 中 650）。
表示される回答は約94トークン分。**orchestration=0 でも「見えない思考コスト」は別枠で存在**する。
→ 「fugu は安い」と即断できない。ダッシュボードは `reasoning_tokens` も追うべき
（`raw_usage` に入っている。schema 昇格の是非は要ユーザー判断）。

### (b) 思考過程が最終回答に漏れることがある
存在しない論文への回答に、英語の内部メモ
`Then explain... Let's refine the response to` が混入した例あり。
**常用の実用性を測るなら「出力フォーマットの安定性」も評価軸に入れる。**

## 4. 「裏(orchestration)」とは何か(公式ドキュメントで確認)

Sakana の公式 pricing/docs による定義:

> orchestration トークンは、Fugu が **サブタスクを委任(delegate)し、中間結果を検証
> (verify)し、統合ロジック(synthesis)を走らせ、自分自身を再帰的に呼ぶ(recursive
> self-call)** ときに消費される。input/output とは別枠の「実トークン使用量」であり、
> **最終価格に計上される。**

フィールド定義(公式):

| フィールド | 定義 |
|---|---|
| `orchestration_input_tokens` | orchestration に使われた入力トークンの総和 |
| `orchestration_input_cached_tokens` | orchestration 入力のうちキャッシュヒット分 |
| `orchestration_output_tokens` | orchestration の出力トークン |

→ 「どの LLM に振るかを決める部分」**だけでなく、委任・検証・統合・再帰呼び出しを含む
裏処理の総量**。当初の推測どおりで、**公式に確認できた**。
`orchestration_input` は裏に食わせた入力、`orchestration_output` は裏が生成した中間出力。

**最重要: 裏トークンは通常の input/output と同レートで課金される。**
つまり「裏トークン比率」はそのまま**支払いの水増し率**に直結する(参考値ではなく実費)。

## 4.5 料金と実コスト例(公式 pricing・2026-07-24 時点・要再確認)

Pay-as-you-go(USD / 1M tokens、`標準 / >272K context` の順):

| モデル | input | output | cached input |
|---|---|---|---|
| fugu-ultra | $5 / $10 | $30 / $45 | $0.50 / $1.00 |
| fugu-cyber | $6 / $12 | $36 / $54 | $0.60 / $1.20 |
| fugu(base) | 未取得(要確認) | | |

サブスク: Standard $20(基準)/ Pro $100(10×)/ Max $200(20×)。基準の具体枠は非公開。

**実コスト計算(前掲 ultra レコード: in297 / out6989 / 裏in16,328 / 裏out9,061):**
裏は同レート課金なので、input系=297+16,328、output系=6,989+9,061:

```
input 系 : 16,625 tok × $5 /1M  = $0.083
output系 : 16,050 tok × $30/1M  = $0.482
合計     ≈ $0.565 / 1リクエスト
（裏なしの見かけ = $0.211。裏が約 $0.354 を上乗せ）
```

**注目: 裏率はトークン基準で 78% だが、金額基準では約 63%。** output レートが input の
6倍なので、可視 output が大きいと「トークン比率」と「金額比率」がズレる。
→ **ダッシュボードはトークン比率だけでなく「金額基準の裏比率」も出すべき**
(判断はお金で行うため)。レートは設定に外出し済み。

[sakana.ai/fugu](https://sakana.ai/fugu) /

## 5. ベンチにできる設問カテゴリ(採点自動化できるものを選ぶ)

「正解が機械判定できる」ことが肝（Fugu と将来のローカル LLM を同一問題で比較するため）。

- **自動採点コード生成**: 関数仕様 → 生成コードを**実行してテスト通過数**で採点。
  正規表現/SQL 生成も、サンプルデータに当てて検証。
- **忠実性(要約)**: 与えた原文を要約 → **原文に無い事実を足していないか**を突合（実務版ハルシネーション検査）。
- **偽前提の訂正**: 「なぜ X は(実際はしていない)Y をした?」→ 訂正できるか。
- **存在しない実体**: 偽の論文/API/関数 → 「無い」と言えるか(捏造率)。
- **決定的計算**: 日付/単位/為替換算 → 厳密一致。
- **構造化抽出**: 自由文 → 指定 JSON スキーマ → バリデーションで採点。
- **オーケストレーション誘発**: 多専門家統合タスク → 裏が出るモデル/条件の切り分け。

各設問を「自動グレーダ(実行・完全一致・スキーマ検証)」とペアにするのが
`reasoning-math-benchmark` の grading.py 思想と同じ。Phase 2 でここに合流できる。

## 5.5 「AI が Fugu を呼ぶ」パターンの所感(エージェント委任視点)

AI(このアシスタント含む)が Fugu をサブモデルとして呼ぶ用途で、実際に叩いて感じた点。

**良い点**
- **base `fugu` は委任先として素直**。コード生成・JSON 抽出・翻訳・論理が正確で、
  tool_call の JSON も綺麗に返る(実測で `{"city":"Osaka"}` を断片から正しく組成)。
  裏 0 なので、単純な構造化サブタスクの委任先として扱いやすい。
- **usage を開示している**。呼ぶ側が「この委任がいくら/どれだけ裏を使ったか」を
  事後に測れる。オーケストレータを自作するとき、この可観測性は貴重。

**エージェント運用で刺さる罠**
1. **reasoning が max_tokens を食い尽くし、可視出力ゼロで課金される**(実測: ultra で
   `completion_tokens=900` が全部 `reasoning_tokens`、本文空、しかも裏12,364)。
   → **ultra を呼ぶときは max_tokens を十分大きく取る**。小さいと「金だけ payして空返し」。
2. **コスト/レイテンシが事前予測不能**。ultra は同種タスクで 73s〜287s とばらつき、
   裏も 78〜91% と揺れる。**エージェントの budget 見積り・timeout 設計が難しい**
   (30〜60s の標準 timeout では ultra は必ず切れる。300〜600s 見ておく)。
3. **思考過程が最終出力に漏れることがある**。プログラムで出力をパースする用途では、
   英語の内部メモ混入が事故になりうる。**厳格な JSON 等が欲しいなら base fugu＋
   スキーマ制約**の方が安全。
4. **冗長・自己紹介の枕**。単純な質問でも「Sakana AI が開発した…」と前置きしたり
   3,000 tok 使うことがある(base でも)。エージェント連鎖では無駄が積み上がる。

**まとめ(委任戦略の私見)**
- **base `fugu`** = 速い・正確・裏0。構造化サブタスク(抽出/変換/短い生成)の委任先に向く。
  ただし reasoning でトークンが膨らむので出力上限は余裕を持って。
- **`fugu-ultra`** = 「専門家チームを1発で回す」用。高価値な単発の統合タスク限定。
  多段のエージェントループで多用すると、遅さ・裏コスト・空返しリスクが積算して割に合わない。

## 5.6 「上手に分散させる」ノウハウ探索 — 実験結果

「Fugu に上手に fan-out(分散)させる」プロンプト側の手はあるか、を実測した。

### 実験A: base fugu は分散するか
- 明示的に「複数の専門サブエージェントに分解・委任し統合せよ」と指示 → **裏 0**。
- 結論: **base `fugu` はプロンプトで fan-out を誘発できない。** 分散はモデル特性。

### 実験B: ultra の裏はプロンプトで制御できるか(同種タスクを条件替え)

| ultra への指示 | elapsed | 表 | 裏 | 裏率 | 本文 |
|---|---|---|---|---|---|
| 「日本の首都は?一語で」 | 5.6s | 35 | **1,260** | 97% | 東京 |
| 同上＋system「委任するな/単一パス」 | 5.8s | 59 | **1,260** | 96% | 東京 |
| 「KPIを1つだけ名前だけ」 | 31.5s | 509 | **7,489** | 94% | MRR |
| 「端的に。要点のみ。KPI6個だけ」 | 9.2s | 274 | **1,260** | 82% | ○ |
| KPI詳細設計(4系統×5・定義/式/目標) | 408.7s | 1,780 | **52,001** | 97% | **空** |

観察:
- **自明な質問(首都)でも裏1,260。裏の「低い床」が無い。** ultra は常に裏で回す。
- **system で「委任するな」と命じても効かない**(裏1,260のまま)。orchestration は
  完全に内部処理でクライアントから制御不能。
- **絶対量が非単調・予測不能**: 「1つだけ」で7,489、詳細版で52,001。タスクの重さと
  裏トークンが素直に比例しない。
- **長いタスクは reasoning が max_tokens を食い切り本文空**(52,001裏を払って出力0)。

### 実験C(追試): `reasoning.effort` は効く — ただし想定と逆向き

公式 get-started に `reasoning.effort`(`high`/`xhigh`/`max`)というノブがあると判明したため、
「クライアントから制御不能」という当初結論を再検証した。**部分的に誤りだった。**

同一の推論負荷タスク(円卓の座席数え上げ)で、条件だけ振った結果:

| 条件 | elapsed | 表 | 裏 | 裏率 | 本文 |
|---|---|---|---|---|---|
| base 既定 | 16.4s | 1,585 | 0 | 0% | ○ |
| base `effort=high` | 15.9s | 1,585 | 0 | 0% | ○ |
| **ultra 既定** | 145.7s / 116.4s | 924 / 1,544 | **22,066 / 17,945** | 96% / 92% | ○ |
| **ultra `effort=high`** | 83.2s / 82.4s | 691 / 1,027 | **14,870 / 13,447** | 96% / 93% | ○ |
| ultra `effort=xhigh` | 191.1s | 1,672 | **26,055** | 94% | **空** |

(ultra の既定/high は再現確認のため 2 回ずつ実施。順序は 2 回とも一貫。)

**判明したこと:**

1. **`effort=high` を明示すると、既定より安く・速くなる**(裏 -25〜33%、レイテンシ -29〜43%)。
   出力の量・質は同等以上だった。**既定は high より重い挙動をする**(既定=high ではない)。
2. **`effort=high` はレイテンシが安定する**(83.2s / 82.4s とほぼ一定)。
   既定は 145.7s / 116.4s とばらつく。エージェント運用の timeout 設計上これは効く。
3. **下げる方向のノブは無い**。公式に用意されているのは `high`/`xhigh`/`max` のみで、
   `low`/`minimal` に相当する値が無い。**`high` が最も安い設定**。
4. **`xhigh` は裏がほぼ倍・レイテンシ2.3倍で、しかも本文空**(reasoning が枠を食い切る)。
   少なくともこの規模のタスクでは払い損。
5. **base fugu では effort は無効**(裏0のまま、reasoning も 1,438 vs 1,439 で不変)。
   外注コストの削減レバーにはならない。

### 結論(修正版): レバーは「モデル選択」＋「ultra なら effort=high を明示」

プロンプト/スコープ/システム指示のどれでも ultra の裏は下げられない。よって:

- **裏コストを避けたい → `fugu`(base)を使う。** 裏0で、抽出/変換/コード/論理など
  大半のタスクを正確にこなす(§2)。
- **多エージェント統合が本当に欲しい → `fugu-ultra`。** ただし
  裏 80〜97%・レイテンシ数秒〜7分・**本文空リスク**を受け入れる。max_tokens は
  大きめ(目安 4,000+)にしないと「払って空返し」。
- **タスクごとに base↔ultra をルーティングする**のが実用上の最適。
  ultra をエージェントループで多用しない(不確実な裏コストが積算する)。
- `fugu-cyber` はアクセス申請制(このキーでは permission_error)。未評価。

> 端的に言えば「上手に分散させるノウハウ」は**プロンプト側には無い**(実験A/B)。
> ただし**パラメータ側に1つだけある**: ultra を使うなら `reasoning.effort="high"` を
> **必ず明示する**(既定より 25〜33% 安く、30〜43% 速く、レイテンシが安定する)。
> それ以外に裏を減らす手段は無く、`xhigh`/`max` は上げるだけなので通常は使わない。

## 5.7 Claude Code / Codex から Fugu を使う(公式 get-started)

公式に「Claude Code を Fugu で駆動する」手順がある。要点と、このプロジェクトへの含意。

```bash
export ANTHROPIC_BASE_URL="https://api.sakana.ai"
export ANTHROPIC_AUTH_TOKEN="fish_..."          # API_KEY ではなく AUTH_TOKEN
export ANTHROPIC_DEFAULT_OPUS_MODEL="fugu-ultra"
export ANTHROPIC_DEFAULT_SONNET_MODEL="fugu"
export ANTHROPIC_DEFAULT_HAIKU_MODEL="fugu"
export CLAUDE_CODE_SUBAGENT_MODEL="fugu"
claude
```

Codex 側は `~/.codex/config.toml` に `base_url = "https://api.sakana.ai/v1"`,
`wire_api = "responses"`、`stream_idle_timeout_ms = 7200000`(2時間)等を設定する。
**公式が2時間のアイドルタイムアウトを推奨している**時点で、ultra の遅さは仕様と分かる。

**重要な構造的含意**: `ANTHROPIC_BASE_URL` は**プロセス全体に効く**ため、
「メインループは Claude、サブエージェントだけ Fugu」という**ハイブリッドはこの方式では作れない**
(全リクエストが Sakana に向く)。`CLAUDE_CODE_SUBAGENT_MODEL` も向き先は同じ base URL。

→ ハイブリッド(Claude が判断し、機械的な下請けだけ Fugu)を実現する手段は
**呼び出し単位で外注する `tools/fugu_offload.py` 方式**しかない。
env 方式は「Claude を Fugu で**置き換える**」ものであって、負担を分担するものではない。

その他:
- 公開モデル: `fugu`, `fugu-ultra`, `fugu-ultra-v1.0/v1.1`, `fugu-cyber`(申請制)。
  コンテキスト 1M トークン。`fugu-ultra-v1.1` のみ `max` に対応(他は `xhigh` にマップ)。
- `/v1/responses`(Responses API)も提供。本アプリは `/v1/chat/completions` を使用。

出典: [console.sakana.ai/get-started](https://console.sakana.ai/get-started)

## 6. 総括(小サンプルの暫定所感)

- **base `fugu`**: 素直で正確、捏造しにくい、速い。普段使いのモデルとして印象は良い。
- **`fugu-ultra`**: 出力の質は高い(移行計画の例は妥当)が、**裏 78〜98% + 初動数分無音**の
  コスト/レイテンシが重い。「専門家チームを組む代わり」に払う価値がある高価値タスク限定か。
- Fugu の美点として、**裏トークンや reasoning を usage で開示している**点は珍しく、
  事後計測(このプロジェクト)と相性が良い。多くのプロバイダはここを隠す。

> 注意: 本メモは十数プロンプト規模の観測。契約判断は日曜までに溜めた実使用データで
> ダッシュボードが幅つきで示すこと（点推定を信用しない）。
