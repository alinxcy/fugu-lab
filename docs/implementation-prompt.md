# Claude Code 実装プロンプト

`claudePlayGround` から `playground-spawn` で派生させた **1 つのリポジトリ**の中で、
`chat/` と `dashboard/` を並行開発する(モノレポ)。

```
fugu-lab/
  CLAUDE.md              このプロジェクトの運用ルール(新規に書いたもの)
  .claude/skills/        playground からコピーしたスキル
  .claude/SKILLS_ORIGIN.md
  schema/usage-record.md データ契約の唯一の正
  chat/SPEC.md           チャットアプリ仕様
  dashboard/SPEC.md      ダッシュボード仕様
```

**プロンプトは 2 つに分割。** 下記 ① と ② を、同じリポジトリの別セッションとして流す。
**まず ① を動かし、動き出してから ② を並行で回す。**

`CLAUDE.md` は自動でロードされるので、各セッションで仕様書を読ませる指示は
念のため入れてあるが、忘れても文脈には入る。

---

## ① チャットアプリ(先に着手・最優先)

このリポジトリで、ローカルファーストのマルチプロバイダ・チャットアプリを実装したい。

まず `chat/SPEC.md` と `schema/usage-record.md` を読んでほしい。方針・アーキテクチャ・スコープはすべて
そこに書いてある。この指示と仕様書が食い違った場合は仕様書を優先し、
食い違いを見つけたこと自体を教えてほしい。

### 状況(重要)

Sakana Fugu を月額契約すべきか、**日曜の朝までに判断する**必要がある。
測定窓は金・土の 2 日間しかない。判断材料は「実際に使って溜まった使用データ」なので、
**このアプリが動き出すのが遅れるほど、判断材料が失われる**。

したがって最優先は完成度ではなく**着手から測定開始までの時間**。
仕様書の Phase 0 の完了条件は「UI が良いこと」ではなく
「**今日、日常の作業で自然に使い始められること**」。

### 今回のスコープ

**Phase 0 のみ**を実装する。Phase 1(`dashboard/`)は別セッションの別作業。
Phase 2 の項目には着手しないこと。

### 絶対に守ってほしいこと

1. **SSE 層はチャンクの `content` 以外を破棄しないこと。**
   `schema/usage-record.md` の「譲れない要件」に詳細がある。ストリーミング時は `usage` が最終チャンクに
   載って届く場合があり、捨てると UsageRecord が成立しない = このアプリの存在意義が
   消える。`tool_calls` も同様に複数チャンクにまたがるため蓄積が必要。
   **チャンクは生のまま保持し、必要なフィールドを後段で取り出す構造にすること。**

2. **UsageRecord のデータ契約を厳密に満たすこと。**
   `schema/usage-record.md` の表とフィールド要件に厳密に従う。特に:
   - `raw_usage`(プロバイダが返した usage を無加工で保存)
   - `orchestration_*`(裏トークン内訳。これが取れないと判断自体が不可能)
   - `ttft_s` と `elapsed_s` を分けて記録
   - 追記専用の JSONL

   取得できなかったフィールドは null で残し、**レコード自体は必ず生成する**こと。

3. **Provider Abstraction Layer を切ること。**
   今回は fugu adapter だけを実装するが、後から LM Studio 等を
   「アダプタ 1 つ追加 + 設定追記」で足せる形にする。認証方式が違う /
   usage のフィールド名が違う / usage を返さない、といったケースを想定して
   インターフェースを設計すること。

4. **Middleware Chain の骨組みを入れること。**
   リクエスト前・レスポンス後にフックを差せる形。今回は usage recorder と
   logger だけでよいが、後から他機能をコアをいじらずに足せることが要件。

5. **設定を外出しすること。** エンドポイント・モデル ID・API キー・従量課金レートは
   コードに埋めない。API キーはブラウザに渡さずサーバー側で保持する。

### Tool Calling は「観測のみ」

`tools` を送れること、返ってきた `tool_call` の delta を蓄積して画面に表示すること、
**引数 JSON が壊れていたらそれが分かる形で表示すること**(壊れて返ること自体が
知りたい情報なので握り潰さない)。**ツールの実行・往復は実装しない**(Phase 2)。

### やらないこと

- usage の集計・累積・コスト計算・枠フィット推定・グラフ(すべてダッシュボード側の担当)
- LM Studio / openai-compat アダプタ(Phase 2)
- tool の実行往復、エージェントループ、MCP(Phase 2)
- UI の作り込み、RAG、会話分岐、並列比較、認証

「あると親切だろう」と思っても足さないこと。迷ったら**入れない方に倒して確認**してほしい。

なお、チャット画面に**1レスポンスごとの実測値 1 行表示**(例:
`8.2s (初動 1.4s) / 3,400 tok — 裏 61%`)は Phase 0 に含む。集計ではなく、
手元の UsageRecord の値をそのまま出すだけのもの。

### 進め方

- 実装前に、**スタックとファイル構成の方針を先に提示**してほしい。合意してから書き始めたい。
- `parse_usage` は、レスポンスのサンプル JSON を固定データにした単体テストを書くこと
  (ネットワーク不要で回せること)。**ストリーミングのチャンク列から usage と
  tool_call を組み立てるロジックも同様にテストすること。** ここが壊れると全部無駄になる。
- 動いたら、実際に Fugu に 1 往復させて JSONL に想定通りのレコードが出ることを
  確認する手順を教えてほしい。

## ② ダッシュボードアプリ(①が動き出してから並行)

`dashboard/SPEC.md` と `schema/usage-record.md` を読んで実装してほしい。

①のチャットアプリが吐く UsageRecord の JSONL を読み、**Fugu と契約すべきか、
するならどのプランかを判断するためのダッシュボード**を作る。

### 絶対に守ってほしいこと

1. **「契約しない」という結論を出せる作りにすること。**
   オーバーヘッドが大きすぎる場合、契約しないのが正解になりうる。
   「どのプランを選ぶか」を前提にした UI にしないこと。

2. **サンプル数の少なさを隠さないこと。**
   測定窓が 2 日しかないため、月間予測は外挿になる。どの集計値にも
   「何件・何日分から算出したか」を添え、サンプルが薄いときは明示的に警告する。
   点推定ではなく幅で示すこと。**少ないサンプルから自信ありげな数字を出すのが
   このアプリ最悪の失敗**で、判断を誤らせる。

3. **裏トークン比率を中心指標として扱うこと。** 参考値ではない。

4. **入力に対して堅牢であること。** 壊れた行・欠損・想定外フィールドがあっても
   クラッシュせず、スキップした事実を表示する。測定中に落ちるのが最悪。

5. **依存は `schema/usage-record.md` の定義のみ。** `chat/` のコードを参照しないこと。

### 読み込みモード

ライブ(ファイル監視で自動更新)を既定とし、バッチ(指定ファイルを読む)も
後から呼べる形で両対応にすること。追記専用なので末尾差分だけ読めばよい。

### やらないこと

- モデル別比較の本格化(データが溜まってから)
- 他サービスとのコスト比較、エクスポート

## 補足(貼らなくてよい・自分用メモ)

- ①が動いた瞬間から測定が始まる。②は①より少し遅れても、金曜夜〜土曜に
  間に合えば判断には使える。
- ②が間に合わなくても、JSONL さえ溜まっていれば使い捨てスクリプトで集計できる。
  最悪の保険はそこ。**①だけは今日中に動かすこと。**
