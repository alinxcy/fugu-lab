# SPEC: Usage ダッシュボードアプリ

## 概要

チャットアプリ(別仕様書)が吐き出す UsageRecord の JSONL を読み、
**「Sakana Fugu と契約すべきか、するならどのプランか」を判断するための
ダッシュボード**を作る。

判断期限は**日曜朝**、測定窓は**金・土の 2 日間**。データが薄い状態で判断する
ことになるため、本アプリの設計上もっとも重要なのは「見栄えの良いグラフ」ではなく
**サンプル数の少なさを隠さず、外挿の危険を明示すること**である(後述)。

### 出せなければならない結論

このダッシュボードは以下の 3 つを等しく出力できる必要がある:

1. **Standard($20)で足りる**
2. **Pro($100)/ Max($200)が要る**
3. **そもそも契約しない方がよい**

3 が重要。オーケストレーションのオーバーヘッドが大きすぎる場合、
「Fugu に払うより他のサービスに払う方が有意義」という結論が正解になりうる。
**「どのプランか」を前提にした UI にしないこと。** 契約しないという結論に
自然に到達できる作りにする。

### 依存方針

- **入力は JSONL のみ。** チャットアプリの内部構造・コード・DB に一切依存しない。
  結合点はスキーマだけ。片方を作り直しても他方が壊れないこと。
- 外部 SaaS への依存を持たない。ローカルで完結する。

---

## 入力データ

`chat/` が吐く UsageRecord の JSONL(1 行 1 レコード)。

**スキーマは `../schema/usage-record.md` を参照。** そこが唯一の正であり、
本仕様書にスキーマを複製しない(同期漏れによる誤集計を構造的に防ぐため)。

本アプリが特に依存するフィールドと用途:

| フィールド | 用途 |
|---|---|
| `timestamp` | 期間集計、時系列推移 |
| `provider` / `model` | プロバイダ別・モデル別の切り分け |
| `input_tokens` / `output_tokens` | 消費量・コスト計算の基礎 |
| `cached_tokens` | 実効コストの補正 |
| `orchestration_input_tokens` / `orchestration_output_tokens` | **オーバーヘッド比率(最重要指標)** |
| `ttft_s` / `elapsed_s` | レイテンシ分析(初動と総時間を分けて) |
| `raw_usage` | マッピング漏れの救済、想定外フィールドの検知 |
| `error` | 失敗率の把握 |

**null と 0 を区別すること。** 「裏トークンが 0 だった」と「裏トークンが
取れなかった」はまったく別の意味を持つ。前者は集計に含め、後者は
「不明」として扱い、母数から除くか明示すること。

### JSONL の場所

`chat/` が書き出す先を設定ファイルで指定できること。相対パス決め打ちにしない。
複数ファイルを指定できるとなお良い。

## 機能仕様

### 1. 消費サマリ(最優先)

期間(全体 / 日別)ごとの集計:

- リクエスト数、成功 / 失敗数
- 入力・出力・キャッシュ・**オーケストレーション**の各トークン合計
- 概算コスト(設定ファイルのレートを用いた計算)

### 2. オーバーヘッド分析(最優先・「契約しない」判断の根拠)

**このアプリの中心指標。**

- **裏トークン比率** = orchestration トークン / 課金トークン総計。
  全体値と、リクエスト単位の分布(どのくらいばらつくか)。
- 比率の時系列推移(使い方によって変動するか)。
- リクエストの種類別の傾向が見えるとなお良い(軽い質問ほど比率が悪化するなら、
  それは常用にとって致命的な情報)。

**判断への接続**: 裏トークン比率が高いということは、支払いの多くが
自分に見えない処理に消えているということ。この値が許容できない水準なら、
プラン選択以前に「契約しない」が結論になる。**その結論に到達できる見せ方をすること。**

### 3. 枠フィット推定(最優先・ただし要注意)

直近の使用ペースから、Standard / Pro / Max のどの枠に収まるかを推定する。

**必須の注意表示**: 測定窓が 2 日しかないため、この推定は**外挿**である。
以下を必ず併記すること:

- 推定の根拠となったサンプル数(リクエスト数・実測日数)
- サンプルが少ない場合の明示的な警告
- 単一の点推定ではなく、**幅**(このペースなら〜、ヘビーに使えば〜)

**サンプル数が少ないときに、それを隠して自信ありげな数字を出すことは、
このアプリにおける最悪の失敗である。** 判断を誤らせる。

### 4. レイテンシ分析(優先度中)

- `ttft_s`(初動)と `elapsed_s`(総時間)を**分けて**表示。
  「待ち時間は気にしない」という前提があるため、総時間だけでは判断できない。
  初動が速ければ総時間が長くても体感は良い。
- 分布(中央値・最大)。平均だけでは外れ値が見えない。

### 5. モデル別比較(優先度低・Phase 2)

`provider` / `model` で切り分けた比較。ローカル LLM のレコードが溜まってから
意味を持つため、チャットアプリ側の Phase 2 以降。

## 読み込みモード

**両方に対応し、後から切り替えられること。**

- **ライブ(既定)**: JSONL を監視し、追記を検知して自動更新。使いながら
  数字が伸びるのが見える。
- **バッチ**: 指定した JSONL を読み込んで表示。過去データの分析、
  複数ファイルの比較に使う。

追記専用ファイルなので、ライブ更新は「末尾の差分を読む」だけで済む。
全体を再読み込みしない実装が望ましい。

## 非機能・開発方針

- **レートは設定ファイルに外出し。** 従量課金レートは変動しうるし一部非公開。
  コードに埋めない。
- **コストは「正確な請求額」ではなく「相対的な重さの指標」として提示すること。**
  この但し書きを UI 上にも明記する。断定的な金額表示は誤解を生む。
- **サンプル数を常に可視化する。** どの集計値にも「何件から算出したか」を添える。
- **入力の堅牢性**: 壊れた行・想定外フィールド・欠損フィールドがあっても
  クラッシュせず、その行をスキップした事実を表示すること。測定中にアプリが
  落ちてデータを見失うのが最悪。
- **言語**: チャットアプリ側と揃えるのが自然(Python 推奨の理由は同 SPEC 参照)。
  ただし本アプリは JSONL しか読まないので、独立に選んでもよい。

## 配置

**`chat/` と同一リポジトリ内の別ディレクトリ(`dashboard/`)。**

結合点は `../schema/usage-record.md` の定義のみ。`chat/` のコードを
参照しない、インポートしない、同じプロセスで動かさない。

同一リポジトリにすることで、スキーマ定義が 1 箇所に保たれる。
別リポジトリにすると定義が 2 箇所に分裂し、同期を怠ったときに
**ダッシュボードが静かに誤った集計を出す**——最も見つけにくい壊れ方になる。
日曜の判断がこの数字に依存する以上、その risk は構造的に排除しておく。
