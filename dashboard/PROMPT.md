# ② ダッシュボード実装プロンプト(別セッション用)

このリポジトリ `fugu-lab` の `dashboard/` を実装する。①チャットアプリはすでに動いており、
`chat/data/usage.jsonl` に UsageRecord を追記している。**別セッション・別作業**として進める。

## まず読むもの

1. `dashboard/SPEC.md` — このアプリの仕様(方針・機能・スコープ)。**正はこちら**。
2. `../schema/usage-record.md` — データ契約。**唯一の結合点**。
3. `../sample-data/README.md` と `../sample-data/usage.sample.jsonl` — 実データのサンプルと知見。
4. (参考)`../chat/tests/fixtures/README.md` — Fugu の実挙動メモ。**読むだけ。コードは import しない。**

この指示と仕様書が食い違ったら**仕様書を優先**し、食い違いを見つけたこと自体を報告してほしい。

## 状況

Sakana Fugu を月額契約すべきか**日曜朝までに判断**する。測定窓は金・土の2日だけ。
データは薄い。ゆえに本アプリの価値は「綺麗なグラフ」ではなく
**「薄いサンプルから誤った確信を生まないこと」**にある。

## 絶対に守ること

1. **「契約しない」を出せる作りにする。** Standard($20)/Pro($100)/Max($200) の
   どれかを選ぶ前提の UI にしない。オーバーヘッドが酷ければ「契約しない」が正解になりうる。
2. **サンプル数を隠さない。** どの集計値にも「何件・何日分から算出したか」を添える。
   月間予測は外挿。**点推定でなく幅**で示し、薄いときは明示警告。
   *少ないサンプルから自信ありげな数字を出すのが最悪の失敗。*
3. **裏トークン比率を中心指標として扱う**(参考値ではない)。
4. **入力に堅牢**。壊れた行・欠損・想定外フィールドでもクラッシュせず、
   スキップした事実を表示する。測定中に落ちるのが最悪。
5. **依存は `../schema/usage-record.md` の定義のみ。** `chat/` のコードを参照・import・
   同一プロセス実行しない。結合点はスキーマ(JSONL)だけ。

## ①実装で判明した実データの重要事実(必ず反映)

- **裏トークンは「表の部分集合」ではなく追加課金される。**
  実測: fugu-ultra で 表 7,286 に対し 裏 25,389。`orchestration_input_tokens`(16,328)は
  `prompt_tokens`(297)を大きく超える。したがって:

  ```
  課金トークン総計 = input_tokens + output_tokens
                     + orchestration_input_tokens + orchestration_output_tokens
  裏トークン比率   = (orchestration_input + orchestration_output) / 課金トークン総計
  ```

  分母を「表のみ」にすると 100% を超える誤りになる。**この定義で統一すること。**
- **null と 0 を区別**。「裏が 0 だった」と「裏が取れなかった(None)」は別。
  後者は母数から除くか「不明」として明示。0 は集計に含める。
- **`ttft_s` と `elapsed_s` は分けて集計・表示**。合算しない。
  実測: ultra は ttft ≈ elapsed(初動まで数分無音)。中央値・最大も出す(平均だけにしない)。
- **`raw_usage` にスキーマ未定義の隠れコストがある**: `reasoning_tokens`
  (ultra で 4,920)、`orchestration_input_cached_tokens` 等。
  `reasoning_tokens` も「課金される見えない出力」であり裏コストの別軸。
  **schema への昇格是非はユーザーに確認**(勝手に schema を変えない)。当面は
  `raw_usage` から拾って「参考」提示に留めるのが無難。未知フィールド出現の検知も歓迎。

## 読み込みモード

- **ライブ(既定)**: JSONL を監視し追記を検知して自動更新。追記専用なので**末尾差分だけ**読む
  (全体再読み込みしない)。
- **バッチ**: 指定ファイルを読む。複数ファイル指定に対応できるとなお良い。
- 入力パスは設定で指定(相対パス決め打ちにしない)。既定は `../chat/data/usage.jsonl`、
  開発時は `../sample-data/usage.sample.jsonl` を読めると便利。

## 機能(SPEC の優先度に従う)

1. 消費サマリ(全体/日別: 件数・成功/失敗・表/裏/キャッシュの各合計・概算コスト)。
2. **オーバーヘッド分析**(裏率の全体値＋リクエスト単位の分布＋時系列＋できれば種類別傾向)。
3. **枠フィット推定**(外挿。サンプル数・幅・警告を必須併記)。
4. レイテンシ分析(ttft/elapsed を分け、中央値・最大)。
5. (Phase 2)モデル別比較。

コストは**「正確な請求額」ではなく相対的な重さの指標**として提示し、その但し書きを UI にも出す。
レートは設定ファイルに外出し(非公開/変動)。

## やらないこと

モデル別比較の本格化、他サービスとのコスト比較、エクスポート、複数期間比較ビュー(すべて後回し)。
「あると親切」でも足さない。迷ったら入れない方に倒して確認。

## 進め方

- **実装前にスタックとファイル構成の方針を提示し、合意してから書く。**
  言語は①(Python)に揃えるのが自然だが、JSONL しか読まないので独立に選んでもよい。
- **JSONL パーサ(壊れた行のスキップ、null/0 区別、裏率計算)は、`sample-data` と
  自作の異常系フィクスチャでネットワーク不要の単体テストを書く。** ここが誤ると
  日曜の判断を静かに誤らせる。最優先でテストする。
- 動いたらライブ更新を実演(①でチャットしながら数字が伸びるのを確認)。

## スコープ規律(このセッションの境界)

- `chat/` のコードは触らない・import しない。
- `../schema/usage-record.md` を変えたくなったら、①にも波及するので**必ずユーザー確認**。
- 完成後、汎用性の高いパターンが生まれたら `skill-harvester`/`skill-creator` で Skill 化を検討
  (playground への還流は `skill-return`)。
