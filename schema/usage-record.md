# UsageRecord — データ契約

**このファイルがスキーマの唯一の正(single source of truth)。**
`chat/` が書き、`dashboard/` が読む。両者の唯一の結合点。

変更するときは、必ず両アプリへの影響を確認すること。ここを変えれば
両方が影響を受ける——それが意図された設計であり、だからこそ定義は 1 箇所にある。

---

## 永続化フォーマット

**JSONL(1 行 1 レコード、追記専用)。**

追記専用であること。途中で壊れても既存レコードを失わない。
ダッシュボード側はライブ更新のため末尾差分だけを読むので、
既存行を書き換える実装にしないこと。

出力先パスは設定ファイルで指定可能にすること(両アプリとも)。

---

## フィールド定義

| フィールド | 必須 | 型 | 内容 |
|---|---|---|---|
| `id` | ✅ | string | レコード一意 ID |
| `timestamp` | ✅ | string | リクエスト送出時刻(ISO 8601、タイムゾーン付き) |
| `provider` | ✅ | string | アダプタ名(`fugu` / `lmstudio` 等) |
| `model` | ✅ | string | 実際に指定したモデル ID |
| `conversation_id` | ✅ | string | どの会話のどのターンかを後から辿るため |
| `ttft_s` | ✅ | number | 最初のトークンが届くまでの秒数 |
| `elapsed_s` | ✅ | number | 完了までの総秒数 |
| `input_tokens` | ✅ | number | 表の入力トークン |
| `output_tokens` | ✅ | number | 表の出力トークン |
| `cached_tokens` | — | number \| null | キャッシュヒット分 |
| `orchestration_input_tokens` | — | number \| null | 裏で消費された入力トークン |
| `orchestration_output_tokens` | — | number \| null | 裏で消費された出力トークン |
| `raw_usage` | ✅ | object | プロバイダが返した usage を無加工で保持 |
| `error` | — | string \| null | 失敗時の内容。成功時は null |

---

## 譲れない要件

### 1. `raw_usage` を必ず無加工で保存する

唯一の保険。プロバイダが想定外のフィールドを返しても、マッピングが誤っていても、
生データが残っていれば後から復元できる。捨てると復元不能。

ダッシュボード側は、`raw_usage` に未知のフィールドが現れたことを検知して
知らせられるとなお良い(プロバイダ側の仕様変更に気づける)。

### 2. orchestration 系フィールドを落とさない

「課金トークンのうち何割が自分に見えない処理に消えたか」は、契約判断の中心指標。
これが取れないとトライアル自体が無意味になる。プロバイダが名称違いで返す
可能性があるため、マッピングできなかった場合も `raw_usage` 経由で拾えること。

### 3. `ttft_s` と `elapsed_s` を分けて記録する

「反応が始まるまで」と「終わるまで」は体感がまったく違う。初動が速ければ
総時間が長くても快適だが、初動が遅ければ同じ総時間でも苦痛。
合算すると後から分離できない。

### 4. null と 0 を区別する

「裏トークンが 0 だった」と「裏トークンが取れなかった」はまったく別の意味。
取得できなかったフィールドは **null** で残すこと。0 で埋めない。
ダッシュボード側も、この 2 つを区別して集計・表示すること。

### 5. レコードは必ず生成する

usage が取れない、一部フィールドが欠ける、リクエストが失敗した——
いずれの場合も**レコード自体は必ず 1 件生成する**。取れなかったフィールドは null。
「取得できなかった」という事実も記録として価値がある。

### 6. SSE 層はチャンクの `content` 以外を破棄しない(最重要)

ストリーミング時、各チャンクは差分(delta)として届き、受信側が連結して初めて
意味を持つ。`content` だけを抜き出して他フィールドを捨てる実装にすると:

- **`usage` が取れなくなる。** ストリーミングでは `usage` が最終チャンクに載って
  届く場合があり、捨てると UsageRecord が成立しない。
- **`tool_calls` も取れなくなる。** tool call の引数は複数チャンクに分割されて
  届くため(`{"ci` → `ty":"Os` → `aka"}`)、蓄積処理が必要。

チャンクは生のまま保持し、必要なフィールドを後段で取り出す構造にすること。

## テスト要件

`chat/` 側は、以下をネットワーク不要の単体テストで検証すること:

- レスポンスのサンプル JSON から usage を正しく取り出せること
- **チャンク列(配列)から usage と tool_call を正しく組み立てられること**

ここが壊れると測定データが全部無駄になる。実装の中で最も優先してテストすべき箇所。
