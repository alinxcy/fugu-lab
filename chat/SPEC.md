# SPEC: ローカルファースト マルチプロバイダ・チャットアプリ

## 概要

Sakana Fugu API と、LM Studio 等で動くローカル LLM を、**同じ OpenAI 互換
`/chat/completions` インターフェース越しに叩けるチャットアプリ**を作る。
本体はローカルで動くサーバー、窓口はブラウザ。

v1 の主目的は「Fugu を常用に耐えるか、**測定窓 2 日間**(金・土、日曜朝に判断)の
従量課金トライアルで見極める」こと。したがって v1 の要は、**1リクエストごとの
`usage`(オーケストレーションの裏トークン内訳を含む)とレイテンシを、欠損なく
構造化して永続化すること**にある。

**最適化すべき変数はビルド時間ではなくデータ蓄積時間。** 鍵は即日入手可能なので、
律速は「実使用データが何日分溜まるか」。測定開始が半日遅れれば判断材料が
1/4 失われる。したがって Phase 0 は「UI の質」ではなく「**今日、日常の作業で
使い始められること**」を完了条件とする。

集計・コスト推定・可視化(いわゆる「計測パネル」)は **v1 スコープ外とし、
外部ツールに委ねる**。理由は、データの捕捉はアプリ本体にしかできない不可逆な
処理である一方、集計と可視化は保存済みデータさえあれば後からいつでもやり直せる
可逆な処理だから。加えて「どの月額プランの枠で足りるか」という問いは 3 日間の
トライアルで答えが出て役割を終えるのに対し、usage の記録自体はローカル LLM
転用後も生成速度の計測として生き続ける——寿命の違うものを同じコアに入れない。

その代わり、**UsageRecord のスキーマ(下記「データ契約」)は本仕様で厳密に定める。**
ここが緩いと記録が欠損し、トライアルのやり直しになる(不可逆)。逆にここさえ
満たされていれば、パネルは誰がいつ作っても成立する。

将来はこのアプリをローカル LLM 専用チャットにも転用する。そのため
「プロバイダの抽象化」「フックで機能を足せるミドルウェア構造」「設定の外出し」
の3点を、v1 のコアに最初から組み込む。この3点さえ守れば、後から並列比較・RAG・
MCP などを、コアをいじらずに追加できる。

### 依存方針

- 外部 SaaS への必須依存を持たない。Fugu も含め、接続先はすべて設定で差し替え可能。
- ローカル完結を基本とする(ローカルサーバー + ブラウザ)。認証・クラウド保存は v1 で持たない。
- Python 資産(別途ある `reasoning-math-benchmark` スキルの `grading.py` /
  `problems.json`)を再利用できる余地を残す。→ バックエンド言語の推奨は後述。

責務分担の要点:

- **HTTP/SSE 層** はブラウザとの中継のみに徹する。モデル固有の知識を持たない。
- **Middleware Chain** がこのアプリの拡張の中心。リクエスト送出前・レスポンス
  受信後にフックを差せる。usage 記録もログ保存も、ここに足すプラグインとして実装する。
- **Provider Abstraction Layer** が各接続先の差異(認証ヘッダ形式、レスポンスの
  usage 内訳の場所など)を吸収する。上位層はどのプロバイダかを意識しない。

## コンポーネント仕様

### 1. Provider Abstraction Layer(コア・拡張の要)

各プロバイダを共通インターフェースに揃えるアダプタ群。最低限そろえる責務:

- `stream_chat(messages, model, params) -> AsyncIterator[chunk]`
  ストリーミングでトークンを流す。
- `parse_usage(response) -> UsageRecord`
  レスポンスから usage を正規化して取り出す。**ここがプロバイダごとに違う。**

v1 で実装する2アダプタ:

- **fugu adapter**: Fugu の OpenAI 互換エンドポイント。usage には
  `input_tokens` / `output_tokens` / `cached_tokens` に加え、
  `orchestration_input_tokens` / `orchestration_output_tokens` 等の内訳が
  返る想定(Fugu の pricing ドキュメントで確認したレスポンス形状)。
  **この裏トークン内訳を UsageRecord に必ず保持する**(下記「データ契約」参照)。
- **openai-compat adapter**: LM Studio ローカルサーバー等。認証不要、
  usage はプロバイダによっては欠落するので、欠落時はトークン数を
  自前で概算(または生成速度 tok/s の計測に切り替え)できる余地を残す。

**既知の限界と補完**: Fugu は1リクエストが裏で複数モデルに fan-out するため、
**リクエスト前のコスト予測は原理的に不可能**。よって本アプリは「事前見積もり」を
一切実装せず、**事後計測(実測 usage の累積)に振り切る**。この設計判断は意図的。

### 2. Middleware Chain(拡張機構)

リクエストのライフサイクルにフックを差せる仕組み。v1 で入れるフック:

- **usage recorder**: `parse_usage` の結果を UsageRecord にして追記保存する。
  v1 の要となるフック(「データ契約」の要件を満たす責務を負う)。
- **logger**: リクエスト/レスポンスの生ログをローカル保存(デバッグ・後の分析用)。

将来この Chain に足す想定(v1 では枠だけ用意し、実装しない):
並列比較ディスパッチ、RAG コンテキスト注入、レート制御、リトライ。

### 3. Usage Recording(v1 の要)

**このアプリが果たすべき最重要の責務。** 全リクエストについて UsageRecord を
1 件生成し、追記専用で永続化する。集計・可視化は行わない(`dashboard/` の担当)。

**スキーマと譲れない要件は `../schema/usage-record.md` を参照。**
そこがデータ契約の唯一の正であり、本節はその実装側の責務を述べるにとどめる。

特に以下は仕様中で唯一、緩めてはいけない箇所:

- `raw_usage` の無加工保存
- `orchestration_*` を落とさない
- `ttft_s` と `elapsed_s` を分ける
- null と 0 の区別
- **SSE 層でチャンクの `content` 以外を破棄しない**

#### スコープ外(意図的にやらないこと)

- 累積集計・期間別合計
- 概算コスト計算
- 「Standard / Pro / Max のどの枠に収まるか」の推定
- グラフ・チャート表示

これらはすべて `dashboard/` の担当。アプリ内に作らないこと。

### 4. Chat View(土台・MUST)

- SSE でトークンを逐次表示(Fugu は遅いので体感上ほぼ必須)。
- system prompt のプリセット切替(アプリの性格・役割を差し替える土台)。
- 会話履歴の保持。**文脈はリクエストごとに毎回全部送る**(ステートレスな
  `/chat/completions` の性質。Store に会話を持ち、送出時に組み立てる)。
- **1レスポンスごとの実測値をその場に1行表示する。**
  例: `8.2s (初動 1.4s) / 3,400 tok — 裏 61%`。
  これは集計でも可視化でもなく、手元にある UsageRecord の値をそのまま出すだけ。
  実装コストがほぼゼロな一方、トライアルの主目的である「レイテンシと
  裏トークン比率の体感」に直結するため、チャット画面の一部として v1 に含める。
  ※ 累積・推定は行わない(それは外部ツールの担当)。

### 5. Tool Calling(観測のみ・Phase 0 に含む)

目的は「Fugu のオーケストレーション層を通したとき tool call が壊れずに返るか」を
**契約判断の材料として確かめる**こと。確かめるだけなら実行までは不要なので、
Phase 0 では観測に限定する。

**Phase 0 でやること(観測):**

- `tools` パラメータをリクエストに載せられること(基本は素通し)。
- 返ってきた `tool_call` の delta を**複数チャンクにまたがって蓄積**し、
  組み上がった関数名と引数 JSON を画面に表示すること。
- 引数 JSON が壊れていた場合(パース失敗)も、それが分かる形で表示すること。
  **壊れて返ることこそが知りたい情報**なので、握り潰さない。

**Phase 2 に回すこと(実行):**

- ツールを実際に呼び出し、結果を返して往復を完了させること。
- エージェントループ(多段の自律実行)、MCP クライアント。

実行の往復は実装コストが重い一方、契約判断に足す情報がほとんど無い(観測で
「壊れずに返るか」は分かる)ため、測定窓 2 日を守る目的で意図的に後回しにする。

> **実装状況(Phase 2 着手・A)**: tool 実行往復を実装済み。ただし判断の目的が
> 「Fugu をコーディングエージェントとして使えるか」に広がったため着手した(その場合
> 往復コスト＝裏トークン/レイテンシの実測こそが判断材料になる)。
> - `app/tools/`(レジストリ＋デモツール `get_weather`)、`app/agent/loop.py`(往復ループ)。
> - `/api/chat` に `execute_tools:true` の**明示 opt-in**でのみ有効(既定は従来どおり観測のみ)。
> - **1 ラウンド = 1 リクエスト = 1 UsageRecord**。往復ごとの裏トークン/レイテンシを記録する。
> - 実行ツールは設定 `tools.allowlist` のもののみ(既定オフの安全弁)。
> - repo を触るツール(read/write/bash)＝**B は未実装**。権限・差分適用・allowlist の
>   安全設計を別途詰めてから足す。

### 6. Config Loader / Store

- **Config**: エンドポイント URL・モデル ID・API キー・従量課金レートを
  設定ファイル(例 `endpoints.json` 相当)に外出し。`reasoning-math-benchmark`
  スキルの `endpoints.json` と形式を揃えておくと、資産を共有しやすい。
- **Store**: 会話・usage・設定のローカル永続化。v1 は単純なファイル or 軽量 DB で可。

## 非機能・開発方針

- **設定の外出し**: 接続先・鍵・レートはコードに埋めない。設定ファイル + 環境変数。
  API キーはブラウザに置かずローカルサーバー側で保持する。
- **プロバイダ非依存**: 上位層(UI・Middleware)は特定プロバイダの知識を持たない。
  新プロバイダ追加 = アダプタ1つ追加 + 設定追記、で完結すること。
- **言語の推奨**: **バックエンドは Python を推奨。**理由は、既存の
  `reasoning-math-benchmark`(Python)の `grading.py` / `problems.json` を
  そのまま import して「チャットしながらベンチマークをバッチ実行」まで将来
  つなげられるため。フロントはブラウザなので JS/TS になる(言語は2つになるが、
  ベンチ資産の再利用価値を優先)。**最終判断は実装エージェントに委ねる**——
  TS フルスタックで統一する選択も、ベンチ資産を諦めてよいなら合理的。
- **テスト方針**: Provider アダプタの `parse_usage` は、プロバイダ実レスポンスの
  サンプル JSON を固定データにして単体テストする(ネットワーク不要で回せること)。
  これは `reasoning-math-benchmark` の grading 自己整合性テストと同じ思想。

## 開発の進め方(フェーズ分け)

**鍵は即日入手できる前提。** よって「鍵待ちの間に何を作るか」ではなく
「**最短で測定を開始するには何が要るか**」で切る。Fugu を最初に持ってくる。

### Phase 0 — 今日中に測定を開始する(critical path)

1. Provider Abstraction Layer の共通インターフェースを定義。
2. **fugu adapter** を実装。`parse_usage` で裏トークン内訳まで取り出す。
3. HTTP/SSE 層。**チャンクの `content` 以外を破棄しない**(上記「譲れない要件」)。
4. Middleware Chain の骨組み + usage recorder フック。UsageRecord を JSONL に追記。
5. 最低限のチャット UI(ストリーミング表示 + 1レスポンスごとの実測値1行表示)。
6. tool call の観測(delta 蓄積 + 表示。実行はしない)。

**完了条件は「UI が良いこと」ではなく「今日、日常の作業で自然に使い始められること」。**
UI の質は判断後にいくらでも上げられるが、失った測定日数は取り返せない。

### Phase 1 — ダッシュボード(Phase 0 と並行・critical path)

7. 蓄積された JSONL を読むダッシュボードアプリ。**`../dashboard/SPEC.md` を参照。**

日曜の判断そのものを作る成果物なので、チャットアプリと並行して critical path に乗る。
両者の結合点は JSONL のスキーマのみ。

### Phase 2 — 判断後(常用が決まってから)

8. **openai-compat adapter**(LM Studio 等)。ローカル LLM 転用はここから。
9. tool call の実行往復、エージェントループ。
10. UI 改善、system prompt プリセットの拡充。

**LM Studio アダプタが Phase 2 に落ちている点に注意。** 締切に貢献しないため。
既知のトレードオフとして、プロバイダ抽象化は本来 2 つ実装して初めて「何が実際に
違うか」が分かるので、Fugu 1 つだけで設計すると Fugu の形に寄った抽象化になる
リスクがある。ただしアダプタは後から安く足せるので、測定日数を失うより軽い。
このリスクを承知のうえで、**インターフェースは「認証方式が違う」「usage の
フィールド名が違う」「usage を返さないプロバイダがある」ケースを想定して切ること。**

## この仕様の背景メモ(判断に迷ったとき用)

- なぜ事前見積もりでなく事後計測か → Fugu は fan-out で事前予測が原理的に不可能。
  かつユーザーの主目的が「実測の使い勝手・コスト感の把握」だから。
- なぜ「記録」だけをコアに入れ、「集計・パネル」を外に出したか → データの捕捉は
  アプリ本体にしかできず、失敗すると復元不能(不可逆)。一方で集計・可視化は
  保存データさえあれば何度でもやり直せる(可逆)。さらに「どの枠で足りるか」の
  問いは 3 日で答えが出て役割を終えるが、usage の記録はローカル LLM 転用後も
  生成速度の計測として生き続ける。寿命と可逆性が違うものを同じコアに置かない。
  結果として、実装が可視化 UI に引っ張られてトライアル開始が遅れる事態も防げる。
- なぜ UsageRecord のスキーマだけ厳密に書いたか → パネルを外に出す代わりに、
  「外部ツールが後から何でも作れるだけのデータが確実に残る」ことを保証する必要が
  あるため。ここが仕様の中で唯一、緩めてはいけない箇所。
- なぜプロバイダ抽象化を v1 コアに入れるか → 本アプリはローカル LLM チャットへの
  転用が最初から視野にあり、Fugu と LM Studio は同じ OpenAI 互換 API のため、
  抽象化 1 枚で両対応でき、後の拡張コストが激減するから。
- なぜ Python 推奨か → 既存ベンチマーク資産の再利用。ただし強制ではない。
- なぜ Fugu を先、LM Studio を後にしたか → 鍵が即日入手できると分かった時点で、
  律速がビルド時間からデータ蓄積時間に変わったため。測定窓は 2 日しかなく、
  開始が半日遅れれば判断材料が 1/4 失われる。LM Studio アダプタは締切に
  貢献しないので後回しにした。
- なぜ tool calling を「観測のみ」にしたか → 知りたいのは「オーケストレーション
  越しに tool call が壊れずに返るか」であり、それは観測で分かる。実行の往復は
  コストが重い割に判断材料をほとんど増やさない。
